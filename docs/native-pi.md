# 纯 PI Agent 接入：状态与验收标准

核对日期：2026-10-31。

**状态：上游模型 API 权限缺失，尚未实现可用的纯 PI 模式。**

`main` 分支及 `v0.3.1` 标签保留当前可用的 ACP 桥接版本。本分支记录下一阶段的前提与验收标准，不更改已部署插件的运行方式。

## 已确认的阻碍

[Perch 官方 FAQ](https://www.perchai.app/faq) 的 “Does Starter or Pro include direct API access?” 条目说明：Starter、Pro 和 Ultra 提供通过官方 Web、Desktop、CLI 使用的托管模型额度；应用内部端点不是公开 API。需要直接模型 API 的用户应联系 Perch 获取 integration plan。

当前插件通过 `perch acp` 的 `session/prompt` 调用 Perch Agent。关闭其本地工具、隔离工作目录、调整提示词或关闭 Skill，均不能让这个 Agent 接口变成原始模型接口。

此前遇到的拒绝类型为 `surface_required`，原因是套餐不包含直接 API 访问。这不是通过修复消息格式或令牌刷新就能解决的故障。本阶段不再重试被拒绝的内部模型接口。

## 完成接入所需的官方信息

1. 允许独立客户端调用的模型 API 权限及认证方式。
2. 官方 Base URL、消息/工具调用/流式响应协议文档。
3. API 实际返回的模型 ID、能力及计费归属；不能假定它们等同于 CLI 选择项。

密钥应由 PI 的凭据存储管理，不写入仓库或插件安装包。

## 目标实现

若官方提供 PI 支持的标准模型协议，插件直接声明该 API 提供商，由 PI 原生模型客户端发送请求。不要为此再套一个 Agent 或无必要的本地转发层。

若官方提供不同的模型协议，适配器只转换传输格式，不组织第二层任务，不生成或执行额外工作流。

认证辅助可以与推理分开，但原生模式的推理路径必须满足：

- 不启动 `perch acp`，不调用 `session/prompt`，不运行 Perch Agent 循环。
- PI 的 system/developer/messages 保持其原生语义，不封装进一条 Perch 用户提示词。
- 不扫描或注入 Perch Skill、persona、记忆或其他 Agent 指令。
- 工具定义、调用 ID、工具结果由 PI 管理，使用原生工具协议；不靠模型输出一段 JSON 来模拟工具调用。
- 流式文本、工具增量、终止原因、用量、取消及错误忠实传递。
- 原生模式遇到权限/接口错误时明确失败，不自动回退 ACP 后仍标注为原生模式。
- 保留已有的套餐用量查询与模型映射功能；它们与 Agent 执行方式分离。

## 验收

先用本地模拟端点验证角色、消息、工具及流式语义，再在获得授权的模型接口上验证最多两个模型：DeepSeek / GPT。

只有实际确认 PI 可以独立加载 Skill、组织上下文、执行工具往返，且推理链路没有 Perch Agent，才可以宣布“Agent 和 Skill 完全由 PI 掌控”。当前版本不满足这个验收标准。
